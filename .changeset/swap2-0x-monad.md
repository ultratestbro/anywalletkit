Monad (`eip155:143`) joins the default chain table: Settler registry `0x00000000000004533Fe15556B1E086BB1A72cEae`, taker Settlers 12 `0xF16D1df42E368e4dd873b1f92ED0670FF4c987eB` (current) and 11 `0x031D28683fFc9936903a31670bC618b8Bc9b65dD` (previous), canonical Permit2, WMON `0x3bd359C1119dA7Da1D913D1C4D2B7c461115433A`; watched like the other chains and covered by `verify:live`. Every chain's `prev(2)` is now watched too, and the Settler in force (`ownerOf(2)`) is a severity-high watch source: a new deployment on a pinned chain refuses native-coin sales from that day. Apps that passed Monad through `chains` can drop the override; Monad swaps are now labelled in activity history. Monad bills the gas limit, not the gas used: every 0x call already goes out with the account's own estimate, and a quote asking for more than 6,000,000 gas is refused.

Activity labelling reads the chain table the provider was built with (`zeroExProvider` / `zeroExRemoteProvider`, `chains`), not only the defaults, so a chain added or re-pinned through `chains` is labelled too; `describeZeroExActivity(tx, ctx, chains?)` takes the table as an optional third argument.

`verify:live`: a chain no RPC answers fails the run (it printed `ok — no RPC for …` before), Monad has a public endpoint, `RPC_<chainId>` may list a fallback (`url,url`), and a failed run ends with `Severity: high` (when a sale through the Settler in force is refused today) and a `Reason:` line that names every chain that is not ok (`Reason: NEW on 1, 8453; unreachable on 143`). With `ZEROEX_API_KEY` it also quotes Monad MON → AUSD (100 MON, native) and USDC → MON (Permit2). No runtime check changed. Monad has no recorded 0x answers yet (they need a 0x API key): `fixtures/pin-eras.json` lists it as unrecorded, and a test holds it to being new in the pin era in force, so its first recordings must land before the next pin raise.
