USDT into TON — and into Tron, opt-in — through the USDT0 Legacy Mesh, from EVM sources only: Ethereum USDT, Arbitrum USDT0 and Celo USD₮ (`0x48065fbBE25f71C9282ddf5e1cD6D6A887483D5e`, by contract — the catalog's Celo `USDT` is a bridged token and is refused; through the engine it needs `allowUnlistedTokens` and `getTokenInfo` or `fromTokenDecimals: 6`) to USDT on `ton:-239` (eid 30343) and `tron:728126428` (eid 30420), one `send` on the chain's `UsdtOFT` with an exact approval to it. The contracts come from docs.usdt0.to (deployments API, Legacy Mesh) and were read on-chain on 2026-11-12 (`token()`, `approvalRequired()`, `endpoint()`, `sharedDecimals()` = 6, `feeBps()` = 3, `peers(30420)` / `peers(30343)` = the Tron / TON OFT). At runtime the provider re-reads, once per provider instance, `token()` and `approvalRequired()` on a chain's mesh OFT before the first mesh quote on that chain, and `peers(dstEid)` before the first quote of each source → destination pair (a mismatch refuses the route; a failed read is not cached, so the next quote reads again; preflight reuses the cached results). `endpoint()` and `feeBps()` are not re-read at runtime: `endpoint` is an immutable of the non-proxy `UsdtOFT`, and the module watch (`watch.json`) follows each OFT's code hash and its `feeBps()`; a fee change reaches a quote through `quoteOFT`'s received amount, which the sealed `minAmountLD` then holds. Limits and fees come from the contract: `quoteOFT` (the pool's credit toward the destination caps the amount, the 0.03 % mesh fee is a `protocol` fee row) and `quoteSend` (the LayerZero fee, sealed with the usual 25 % refunded headroom). The recipient is encoded as the destination OFT reads it — Tron base58check → 20 bytes left-padded, TON raw or `EQ…` / `UQ…` → the account hash on workchain 0 (other workchains and testnet addresses are refused) — and every built send is decoded back against the request before it is returned. Right before signing, `preflightDeposit` decodes the deposit again and, before any network read, holds all of it to the sealed send: the target is the source chain's mesh OFT and the transaction is on that chain, the call is `send` (not `quoteSend` / `quoteOFT`, which carry the same `SendParam`), all seven `SendParam` fields are the ones built (`extraOptions`, `composeMsg`, `oftCmd` empty), `MessagingFee.nativeFee` is the sealed fee with `lzTokenFee` 0, and the refund is the sealed refund address; then the pins, the current `quoteSend` (it reverts with `InsufficientCredits` when the pool can no longer pay) within the sealed fee, and `msg.value` = that fee. Its refusals: "usdt0: deposit target … is not the <chain> Legacy Mesh OFT", "usdt0: quote carries no sealed send parameters", "usdt0: quote carries no sealed refund address", "usdt0: the deposit is not the sealed Legacy Mesh send" (undecodable, or `dstEid` / `to` / `amountLD` / `minAmountLD` differ), "usdt0: the deposit calls <function>, not send(SendParam, MessagingFee, refund)", "usdt0: the deposit's SendParam.<extraOptions | composeMsg | oftCmd> <hex> is not the sealed 0x", "usdt0: the deposit's MessagingFee.nativeFee <n> is not the sealed <n>", "usdt0: the deposit's MessagingFee.lzTokenFee <n> is not 0", "usdt0: the deposit refunds <address>, not the sealed refund address <address>", "usdt0: the deposit is for <chain> (chainId <n>), not <chain name> (<CAIP-2>)", then "usdt0: LayerZero fee rose to … — re-quote" and "usdt0: transaction value … is not the quoted fee …". Tracking uses the same LayerZero Scan message; a TON delivery completes only when tonapi (`GET /v2/events/{hash}`, new option `tonApiUrl`, default `https://tonapi.io`) shows the USDT jetton paid to the recipient.

New option `meshDestinations` (provider, `Usdt0Swap2Protocol`, and an optional argument of `usdt0.supportsChain` / `supportsSourceChain` / `supports`): default `["ton"]`, `["tron", "ton"]` adds Tron, `[]` leaves the mesh out. Tron is opt-in because the LayerZero fee into Tron (live 2026-11-12: ≈ 0.0053 ETH from Ethereum / Arbitrum, ≈ 170 CELO from Celo, before headroom) is above the engine's native-fee ceiling in `protocol-swap2-core` (0.005 ETH, 100 CELO), so `swap2` would refuse to execute it; into TON (≈ 0.00007 ETH, ≈ 2.2 CELO sealed) fits. Tron and TON are destinations only: no pair starts there.

Refusal texts are unchanged for every input that was refused before and is not a new route: a Tron / TON source, an EVM source without a mesh OFT (BNB Chain, OP, HyperEVM …) into Tron / TON, and a mesh destination left out of `meshDestinations` still get "USDT0 is not deployed on this chain" from `getQuote`; the first two still get "not a USDT0 route between two deployments" from `usdt0VerifyQuote` (which has no options: it verifies a remote mesh send into either destination). Behaviour changes for existing callers: `supportsChain` is now true for `ton:-239` (with an RPC for any mesh source) and for Celo (a mesh source, with an RPC for Celo), and `usdt0VerifyQuote` holds a route from Ethereum / Arbitrum / Celo into Tron / TON to `usdt0VerifyMeshSend` (an app that runs USDT0 behind `remoteProvider` needs this version on the device to accept mesh quotes; an older client refuses them). New exports: the mesh tables and helpers (`USDT0_MESH_SOURCES`, `USDT0_MESH_DESTINATIONS`, `USDT0_MESH_DEFAULT_DESTINATIONS`, `meshDestinationOn`, `meshRecipientBytes32`, `meshRecipientMatches`, `usdt0VerifyMeshSend`, `usdt0.supportsSourceChain`, type `Usdt0MeshFamily`, …), `TON_API`. `usdt0Pins` now also pins each chain's mesh OFT as call target and spender (Ethereum, Arbitrum, Celo). Existing USDT0 OFT routes are unchanged (same intents, amounts, fees and calldata as 0.4.4, checked live on 8 corridors).
