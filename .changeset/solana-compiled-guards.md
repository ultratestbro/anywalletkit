`sendTransaction` / `signTransaction` / `quoteSendTransaction` refuse the drainer shapes `sendSerialized` already refused, for every input form (kit message, kit `Transaction`, base64 wire): System `Assign` / `Allocate` / `AssignWithSeed` / `AllocateWithSeed` touching this wallet's account, a `CreateAccount` / `CreateAccountAllowPrefund` whose new account is this wallet (paying for another account is fine), `AuthorizeNonceAccount` by this wallet, a Token / Token-2022 `SetAuthority` / `UpdateTokenMetadataUpdateAuthority` / `UpdateTokenGroupUpdateAuthority`, a token `Batch` (its inner instructions are not checked), lamports moved by an instruction the description does not show as a transfer (`CloseAccount`, `WithdrawExcessLamports`, `UnwrapLamports`, `WithdrawNonceAccount`, `TransferSolWithSeed`) to anyone but this wallet, and an undecodable System / Token instruction. They throw `UnsafeTransactionError` (`code`: `core-instruction`, `sets-authority`, `closes-account`, `moves-lamports`) before anything is signed. A program the wallet signs for can still do these by CPI; `sendSerialized` proves the outcome by simulation instead. An instruction whose accounts sit in a lookup table that was not resolved is judged by its name (`describeTransaction` now reports `instruction` on such `unknown` items), so a close whose destination hides in a table is refused too. Everyday shapes still sign: transfers, burns, closes to this wallet, durable nonces, `Allocate` + `Assign` of a fresh co-signer account. New `allowAuthorityChanges` in `SolanaConfig` opts the general path out (a token launch that renounces its mint authority); `sendSerialized` stays strict regardless. Audit 2026-10-25 (post-release), H1. `describeTransaction` now decodes `CreateAccountWithSeed` as a `create-account` item (payer, derived account, lamports, owner) instead of an opaque program call.
