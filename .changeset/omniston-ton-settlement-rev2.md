TON ↔ EVM orders quote again, on Omniston's new TON Escrow Minter only. Since 2026-11-10 Omniston names `EQDybO88l2lrrAmALRUqpmgEE_tuxk510F4Yd4xjbQZxC9IA` (rev2) in every TON ↔ EVM quote, and the SDK refused them all ("untrusted TON settlement contract" / "untrusted ton:-239 settlement contract"). `AUDITED_OMNISTON_SETTLEMENT_CONTRACTS["ton:-239"]` now lists rev2 only, and `DEFAULT_OMNISTON_TON_CODE_HASHES.position` pins only `eb503578…`, the code of the positions rev2 deploys for EVM → TON orders; the two changes ship together. The old minter `EQAbWJ3Y1HgIIvcMq1prG1anlDC0T3cZlAU7luPT6LmTpmrZ` (rev1) and its position code `e4d5115a…` are no longer trusted by default: Omniston's resolvers moved to rev2, and rev1 lacks the escrow-code whitelist rev2 checks every order against. A quote or build that names rev1 is refused with its address in the reason, and a rev1 output position fails `position-code-hash`. Every other pin is unchanged (escrow, execution, authority key, output escrow, position stages). Old rev1 orders need nothing: `OMNISTON_ESCROWS` lists both minters (it recognizes history and grants no trust), so `describeActivity` tags TON → EVM orders on either minter as `bridge`, and `trackIntent` reads no trust table. Every disclosure check refuses a quote older than 6 hours, so a rev1 order quoted before the switch can no longer be closed by any version; it is cancelled after its timelocks. Only an EVM → TON order quoted on rev1 less than 6 hours before an app deploys this version needs `positionCodeHashes` with both position codes to complete, until those 6 hours are over; that pin trusts no new order. Listing rev1 in `trustedSettlementContracts` or `trustedProtocolAddresses` trusts it again for new orders and does not help close an old one. A refund backstop that looks for the input coming back from a minter should read `OMNISTON_ESCROWS` (exported by the package root, not by `/validators`) too, not only the trusted table. The rev2 minter was reviewed read-only: same admin as rev1 and as the STON.fi DEX v2 routers, no upgrade done or pending, and its code differs from rev1 by the escrow-code whitelist (the pinned codes plus one TON ↔ TON code the SDK does not pin), a one-value check on the escrow sub-VM, and a refund path for a failed position deploy that credits the amount back to the same account; replaying both minters' real traffic through rev1 and rev2 gave the same outputs. No API change. Apps that check TON → EVM builds or EVM → TON positions on the device (a mobile app, an extension) need a build with this version too: an older client refuses rev2 even when the server is bumped. If your server sets its own settlement table (for example from an `OMNISTON_TRUSTED_SETTLEMENT_CONTRACTS` env), it replaces the built-in one: list rev2 under `ton:-239`, and leave rev1 out.
