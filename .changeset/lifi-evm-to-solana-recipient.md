LI.FI routes from an EVM chain to Solana work through Mayan, Polymer CCTP and Chainflip. Up to 0.7.0 every such quote was refused ("the recipient on a non-EVM destination sits in bridge-specific data and cannot be checked here"), because `BridgeData.receiver` is only LI.FI's non-EVM placeholder and the Solana recipient sits in the bridge's own data. The module now reads it there, on the device, for the bridges whose transaction binds the delivery to it, and holds it to the requested recipient and token:

- Mayan (`mayan`, `mayanMCTP`, `mayanFastMCTP`): the facet's `nonEVMReceiver` and the destination address inside the Mayan order or transfer (Swift v2, MCTP `createOrder` / `bridgeWithFee`, Fast MCTP `createOrder` / `bridge`) must both be the recipient; the order must go to Solana, carry no custom payload and name the requested mint. Other Mayan entry points are refused.
- Polymer CCTP (`polymer`, `polymerStandard`): CCTP mints to a token account the facet cannot check; it must be the recipient's USDC associated token account, derived on the device.
- Chainflip: the 32-byte destination address and the Solana asset (SOL, USDC, USDT).

`BridgeData` must name LI.FI's Solana chain id and exactly the non-EVM placeholder. EVM → Solana requests ask LI.FI for those bridges only (`allowBridges`; a `chooseRoute` pick is kept among them), so pairs are not lost to a bridge the module refuses. Refused for this direction, each with a named reason: NEAR Intents and LayerSwap (they pay a deposit address whose off-chain order names the recipient), Smart Deposits (a deposit address outright), and LI.FI Intents (its escrowed order names its own oracles, output settler and output amount multiplier, which are not pinned here, so a matching recipient would not bind the delivery). Other bridges to Solana keep the existing refusal text. `lifiVerifyQuote` / `lifiPins` run the same check on a remote quote.

Dry quotes priced for a placeholder no longer carry a transaction. A dry request without `refundAddress` is priced for a placeholder sender (vitalik.eth, or the public BIP-39 "abandon" account from Solana), and a dry EVM → Solana request without `destAddress` for the "abandon" account as the recipient. LI.FI's transaction for such a quote would pay or refund that public account from whichever wallet signed it, so the quote keeps only its price: no `txRequest`, and `providerData.placeholder` set to `"sender"` or `"recipient"`. `buildDeposit` refuses it by name (also with a transaction attached), and `lifiVerifyQuote` / `lifiPins` refuse a quote for such a request that carries a transaction, while a price-only one is still held to the request's amount, floor and route. What to do: an app that built or displayed the transaction of a dry LI.FI quote without the sender (or, to Solana, without the recipient) must pass both addresses; dry quotes with both, and dry EVM → EVM quotes with a `refundAddress` but no recipient (priced for the sender's own address), are unchanged.

EVM → EVM routes, LI.FI Intents between EVM chains included, and Solana-source requests are unchanged. New dependencies: `@noble/curves` and `@noble/hashes` (the associated-token-account derivation). Apps that kept LI.FI away from EVM → Solana pairs can stop doing so.
