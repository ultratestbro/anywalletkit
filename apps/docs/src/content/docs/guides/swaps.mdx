One interface covers same-chain swaps and cross-chain transfers. A **router** asks every
provider you install in parallel, checks each quote the same way, ranks the routes and
executes the one you choose. Snippets on this page come from [`examples/swap`](https://github.com/ultratestbro/anywalletkit/tree/main/examples/swap), which our CI
typechecks and tests.

## Install

```sh
npm install @anywalletkit/protocol-swap2-router \
  @anywalletkit/protocol-swap2-lifi @anywalletkit/protocol-swap2-near-intents \
  @anywalletkit/protocol-swap2-thorchain @anywalletkit/protocol-swap2-chainflip @anywalletkit/protocol-swap2-symbiosis \
  @anywalletkit/protocol-swap2-cctp \
  @anywalletkit/protocol-swap2-usdt0 \
  @anywalletkit/protocol-swap2-uniswap @anywalletkit/protocol-swap2-wrap \
  @anywalletkit/protocol-swap2-jupiter
```

The router bundles no provider. Only the providers you install and pass in end up in your
app, and each provider also works on its own without the router.

### Curve

`@anywalletkit/protocol-swap2-curve` swaps on Curve Router NG straight from the contracts: the
router's own `get_dy` prices each candidate route and its explicit-receiver `exchange` executes the
best one, paying only the recipient and reverting under the minimum (never 0). Routes cross one or
two pools, and only pools from a curated allowlist the package pins — generated by
`scripts/build-allowlist.mjs`, checked on-chain (code hash, coins, TVL, age) and reviewed in the
diff. Between two pools a route only passes through a catalog token, the native coin or the pinned
wrapped native; the registered fake-USDT pool and the pools drained in 2023 are refused whatever a
list says. The router's code hash and version are checked before the first quote on a chain, and
right before broadcast the module re-checks the sealed call, each pool's code and coins, and a fresh
`get_dy` against the minimum. On Ethereum the v1.2 router also swaps crvUSD ↔ scrvUSD in one step.

```ts
import { curveProvider } from '@anywalletkit/protocol-swap2-curve'

const curve = curveProvider({ rpcUrls: { 1: ['https://eth.example/rpc'], 42161: ['https://arb.example/rpc'] } })
```

Routers are pinned on 18 EVM chains; a chain is offered only where the allowlist has pools and you
pass an RPC (Ethereum, Arbitrum, Base, OP Mainnet, Gnosis, Monad, Plasma and X Layer today).

- **MEV on Ethereum.** The minimum caps what a sandwich can take at your slippage; it does not stop
  one from taking up to that. Keep the default small slippage on stable pairs and send Ethereum
  swaps through an MEV-protected RPC (a private transaction relay) where you can.
- **No gas limit in the quote.** The router call carries none: the wallet estimates the exact call
  (with headroom) right before broadcast, after any approval. A per-step formula ran some routes out
  of gas and overcharged where the limit is what you pay (Monad).
- **Behind a backend:** `remoteProvider({ name: 'curve', baseUrl, ...curvePins })` checks the call
  on the device; `...curveRemotePins({ rpcUrls })` also checks the build on chain and holds the
  backend's output and minimum to a fresh `get_dy` within the slippage, so the minimum is the
  device's own. If the backend provider sets `defaultSlippageBps`, pass the same value here.

### Relay

`@anywalletkit/protocol-swap2-relay` talks to Relay's own API and verifies the whole order on the
device before anything is signed. A Relay deposit names an order only by its hash; the module asks
for the order behind it, recomputes the hash (EIP-712 `hashStruct`, Relay's types) and requires it
to be the id in the deposit calldata, requires the solver's signature to recover to the pinned
signer, and holds the order to the request: recipient, both chains, both tokens, the exact input
amount, the minimum, the deadlines and every refund recipient. The deposit and the exact ERC-20
approval are then built locally for the depository pinned in the package, never taken from the API.

```ts
import { relayProvider } from '@anywalletkit/protocol-swap2-relay'

const relay = relayProvider() // or { baseUrl: 'https://your-backend.example/relay' }: see the proxy note below
```

- **Named refusals.** A refused quote reads `relay: <what was found> [<code>]` and reaches
  `onRefusal`; through the router it shows in `lastRejections`.
- **What it does not take.** Routes where Relay swaps on the source chain first (the transaction
  would not call the depository), orders with destination calls or their own fees, the
  whole-allowance deposit, and non-EVM chains.
- **Unfilled orders.** Relay refunds on the source chain to the sender; status reports
  `refund-pending` / `refunded`. Status is read from Relay unauthenticated and is for display only.
- **Behind a backend:** `remoteProvider({ name: 'relay', baseUrl, ...relayPins })` runs the same
  checks on the device against the quote and the built transaction.
- **What a proxy or backend can still do.** It cannot change the recipient, chains, tokens, refund
  addresses or the minimum shown. It can make the quote worse: the solver signs whatever request
  reaches Relay, so one forwarded with an app fee or a gas top-up returns a genuine order with a
  lower amount. The module refuses a quote that accounts for either and always names the slippage
  (yours, else 2 %), but the price itself is bounded only by your `minAmountOut` or the router's
  other quotes.
- **One deposit per order.** Cleared order ids are remembered for the JS realm; pass `clearedStore`
  to keep them across app restarts.

The router is bound to one account: the source of the swap. Its chain is the source chain.

## 3. Describe the swap

<Snippet file="swap/src/swap.ts" region="options" />

- `fromToken`: a token on the **source** chain, as its contract address or a catalog symbol
  (`'USDC'`, `'ETH'`).
- `toToken`: the token on the **destination** chain, as that chain's own id: a contract
  address, a Solana mint or a TON jetton master. A symbol that does not exist in the catalog
  of the destination chain leads to "no route".
- Tokens outside the catalog (the user's own) need `allowUnlistedTokens` on the engine: see
  [Custom tokens](/guides/tokens/#swap-it).
- Omit `toChain` for a same-chain swap.
- Amounts are `bigint` in base units. Use `toTokenAmount` instead of `fromTokenAmount` for
  exact-output swaps.

## 4. Quote

<Snippet file="swap/src/swap.ts" region="quote" />

Show the user `toTokenAmountMin`, not `toTokenAmount`: it is what the route guarantees.

## 5. Let the user pick a route

<Snippet file="swap/src/swap.ts" region="routes" />

Routes come back ranked by value. Two of them are tagged:

- **`best`**: the highest value. Routes within 0.2% of each other count as the same price;
  inside that band the faster and more reliable route wins.
- **`fastest`**: the lowest estimated time.

For a real USDC Ethereum → Base quote on 100 USDC, this returned four routes: CCTP
tagged `best` (99.989 USDC guaranteed, ~3 minutes), LI.FI tagged `fastest` (99.735 USDC,
seconds), then NEAR Intents and THORChain. For 25 USDT from Ethereum to USDT0 on Arbitrum,
USDT0 came out `best` (exactly 25 guaranteed, ~17 minutes) and LI.FI `fastest`.

Pass `valueUsd: usdValue(prices)` to the router to rank on net USD value. Gas and native
bridge fees are then subtracted.

## 6. Execute

<Snippet file="swap/src/swap.ts" region="execute" />

Before anything is signed, the router fetches a live quote from the chosen provider and
checks it against what you showed:

- the output is not below your `minAmountOut`;
- the recipient, amounts and chains match the request;
- the transaction sends exactly the quoted amount, and any transfer or approval inside it
  names only your account, the quoted deposit address or the declared spender;
- aggregator calls go only to that provider's audited contracts.

A route that fails any check is refused, and nothing is sent. ERC-20 approvals are for the
exact amount, never unlimited, and are revoked again if the swap fails after approving. On
Ethereum, USDT is reset to zero first, as that token requires.

## 7. Track delivery

A cross-chain swap finishes on another chain, minutes later. Poll its status with the id
returned by `swap2()`:

<Snippet file="swap/src/swap.ts" region="status" />

| Status | Meaning |
|---|---|
| `pending` | In flight |
| `action-required` | Two-phase route (CCTP): the user must claim on the destination chain |
| `completed` | Delivered |
| `refund-pending` / `refunded` | The provider is returning / has returned the funds |
| `failed`, `expired`, `cancelled`, `partial` | Final, not delivered in full |

The id is a string (`awk1.<provider>.…`). Store it with the user's activity: it is all you
need to resume tracking after an app restart.

### Refusal reasons

A refusal keeps its text, which is meant for logs and support. To decide what to show the user, switch on its
`reason` instead of matching the text. `refusalOf(err)` reads the reason from the error, or from the first error in
its `cause` chain that has one:

```ts
import { refusalOf } from '@anywalletkit/protocol-swap2-core'

try {
  await swaps.quoteSwap2(options)
} catch (err) {
  const refusal = refusalOf(err)
  switch (refusal?.reason) {
    case 'amount_too_small': return show('Increase the amount')
    case 'unsupported_pair': return show('This pair is not supported')
    case 'rate_limited': return retryIn(refusal.retryAfterMs ?? 5_000)
    default: return show('No route right now')
  }
}
```

| `reason` | Meaning |
|---|---|
| `no_route` | The venue has no route for this request, or the venues that sat out did so for different reasons |
| `unsupported_pair` | The venue does not serve this chain, token, pair, direction or flow |
| `amount_too_small` / `amount_too_large` | Outside the venue's limits (fees above the output count as too small) |
| `insufficient_liquidity` | The venue reports too little liquidity for the amount |
| `rate_limited` | The venue throttled the request. `retryAfterMs` is set when it said how long to wait |
| `key_rejected` | The venue rejected the API key, or its absence |
| `upstream_unavailable` | The venue failed, timed out or answered in another shape. `httpStatus` is set when there was one |
| `chain_halted` | The chain, its trading, or the venue's handling of it is halted or paused |
| `recipient_unverifiable` | The transaction does not bind the delivery to a recipient the SDK can check |
| `recipient_mismatch` | The transaction pays or refunds an address other than the requested one, or one that cannot receive |
| `vault_mismatch` | The deposit target (vault, inbound address, router, escrow, settlement contract) is not the confirmed or pinned one |
| `stale_node` | The node or indexer that answered trails the chain too far to be trusted |
| `quote_expired` | The quote or its deadline ran out |
| `price_check_failed` | The output, floor, slippage or value fails the check |
| `simulation_failed` | The transaction reverted in simulation or preflight |
| `policy_refused` | A policy of your app or of the SDK refuses it: fee caps, sponsorship, a disabled provider, addresses the app did not allow |

Where the reason travels:

- **The engine's "no route available"** (`Swap2QuoteError`) has `refusals`: each venue's refusal as
  `{ provider, message, reason?, retryAfterMs?, httpStatus? }`. Its own `reason` is the venues' shared reason, or
  `no_route` when they differ. A venue that sat out without a text (disabled, or not serving the pair) is listed too,
  with an unchanged message.
- **The router** keeps the same list in `lastRefusals`, next to `lastRejections`, and in `RouteSet.refusals`.
- **`onRefusal`** gets the classification as a second argument: `onRefusal(text, { reason, retryAfterMs?, httpStatus? })`.
- **A swap2 server** adds `reason` (and `retryAfterMs`, `httpStatus`) to its error bodies and to `noQuote`. The
  `remoteProvider` stub puts it back on the error. A status alone also classifies: 429 → `rate_limited` (with
  Retry-After), 401 / 403 → `key_rejected`, 408 / 425 / 5xx → `upstream_unavailable`.
- **Provider pins** (`lifiPins`, `thorchainPins`, …) classify their own refusal texts through `reasonOf`, so a remote
  stub's "fails this app's own check" carries a reason too.

A refusal without `reason` is not classified. A wallet's `SimulationError` keeps its own `reason` field (the revert
text): check `err.name === 'SimulationError'` for those.

## Fee caps

`maxNetworkFeeBps` and `maxProtocolFeeBps` (basis points of the input) refuse routes whose
**itemized** fees are above the cap. The check is fail-closed: a route whose provider does
not itemize its fees is refused whenever a cap is set. With caps on, the USDC example above
keeps only the CCTP route. To protect the user without losing routes, compare the
guaranteed output (`toTokenAmountMin`) instead.

### Native fee ceiling

Some bridges charge native coin on top of the input (a LayerZero messaging fee, for example),
declared in the quote. `swap2()` refuses such a fee above the chain's cap: 0.005 ETH on
Ethereum and on chains without a cap of their own (Arbitrum, Base, …), 100 CELO on Celo,
20 POL on Polygon, and so on. The error reads
`swap2: quoted native fee <fee> exceeds the cap <cap> for <chain>`.

To allow one route above it, set `nativeFeeCeiling` on the router (or on any swap2
protocol). The engine calls it for every execution pass whose quote declares a native fee, before
that pass's review screen and approvals: once, unless the quote expires during an approval and the engine
re-quotes (the fresh quote is asked again, and a refusal then revokes the allowance just granted):

| The hook returns | Result |
|---|---|
| a non-negative `bigint` | the cap for this execution, higher or lower than the chain's (`0n` refuses any fee) |
| `undefined` | the chain's cap, as without the hook |
| anything else, or throws | the swap is refused (`Swap2ConfigurationError`) |
| more than `ctx.maxCeiling` (20 × the chain's cap: 0.1 ETH on Ethereum, 2000 CELO on Celo) | the swap is refused |

No answer removes the cap. Return `undefined` for every route you do not mean.

USDT0 Legacy Mesh into Tron is the case this was built for. Its LayerZero fee was
0.005341 ETH from Ethereum and Arbitrum and 170.5 CELO from Celo on 2026-11-12. With the
provider's 25 % headroom the quote declares 0.006676 ETH and 213.1 CELO, both above the
default caps. Tron is LayerZero endpoint 30420, and the `usdt0` provider's mesh intent ids
read `usdt0-mesh:<source eid>:<destination eid>`:

```ts
const TRON_MESH_CEILING = new Map([
  ['eip155:1', 10n ** 16n],             // 0.01 ETH on Ethereum
  ['eip155:42161', 10n ** 16n],         // 0.01 ETH on Arbitrum
  ['eip155:42220', 300n * 10n ** 18n],  // 300 CELO on Celo
])

const swaps = new RouterSwap2Protocol(account, {
  fromChain: account.chain,
  providers,
  nativeFeeCeiling: ({ provider, intentId, fromChain, destChain }) =>
    provider === 'usdt0' && destChain === 'tron:728126428' && /^usdt0-mesh:\d+:30420(?:~|$)/.test(intentId)
      ? TRON_MESH_CEILING.get(fromChain)
      : undefined,
})
```

`destChain` is always the catalog id (`tron:728126428`), even when you passed
`tron:0x2b6653dc`. Through a swap2 server the intent id ends in `~<token>`, which the
pattern above allows. The cap applies only when the swap executes: `quoteSwap2Routes` still
lists a route whose fee is above it.
