One interface covers same-chain swaps and cross-chain transfers. A **router** asks every
provider you install in parallel, checks each quote the same way, ranks the routes and
executes the one you choose. Snippets on this page come from [`examples/swap`](https://github.com/ultratestbro/anywalletkit/tree/main/examples/swap), which our CI
typechecks and tests.

## Install

```sh
npm install @anywalletkit/protocol-swap2-router \
  @anywalletkit/protocol-swap2-lifi @anywalletkit/protocol-swap2-near-intents \
  @anywalletkit/protocol-swap2-thorchain @anywalletkit/protocol-swap2-chainflip @anywalletkit/protocol-swap2-symbiosis \
  @anywalletkit/protocol-swap2-cctp \
  @anywalletkit/protocol-swap2-usdt0 \
  @anywalletkit/protocol-swap2-uniswap @anywalletkit/protocol-swap2-wrap \
  @anywalletkit/protocol-swap2-jupiter @anywalletkit/protocol-swap2-0x @anywalletkit/protocol-swap2-across \
  @anywalletkit/protocol-swap2-stargate
```

The router bundles no provider. Only the providers you install and pass in end up in your
app, and each provider also works on its own without the router.

### Uniswap v4

`@anywalletkit/protocol-swap2-uniswap` quotes Uniswap v3 by default. `v4: "native-in"` adds Uniswap v4 for a native-coin
input: the chain's pinned hookless v4 pools (a generated list shipped with the package, plus your own `v4ExtraPools`)
are quoted on the V4Quoter beside v3 (at one pinned block when `maxPriceImpactBps` is set, else each read at
`latest`), and the larger output wins; the swap runs through the pinned
Universal Router 2.1.2 with the coin as `value`, no approval. `v4: "all"` adds token input (into a token or the native
coin) the same way, through Uniswap's SwapProxy: the token is approved to the chain's pinned SwapProxy for exactly the
input, and the provider simulates that approval and the exact swap from the sender before it returns the quote
(`eth_simulateV1`, or on Monad an `eth_call` with the allowance set by a state override) — nothing is approved for a
swap that would revert. A read of that check the RPC did not answer refuses the quote (`rate_limited` /
`upstream_unavailable`); it never returns the v3 quote in its place.

```ts
uniswapProvider({rpcUrls, v4: "all", maxPriceImpactBps: 500}) // or "native-in"; the gate is optional and applies to the winner
```

- Hookless pools only (no hook allowlist), LP fee ≤ 10% (`v4MaxFeePips`). A failed pool or quote read refuses the
  quote (`rate_limited` / `upstream_unavailable`) instead of quoting from fewer pools. A candidate that needs more gas
  than one transaction on the chain may have (read again at that cap, straight to the quoter) is ranked out and counted
  (`providerData.v4Unexecutable`) where the module knows the chain's per-transaction or execution cap (Ethereum, OP,
  BNB, Unichain, World Chain, Base, Ink, Linea, Arc, Polygon, Monad, Arbitrum, Robinhood Chain); elsewhere (Avalanche,
  Celo, X Layer, MegaETH, Elysium) such a call still refuses the quote.
- With `"native-in"`, token input and native output stay on v3.
- With v4 on, a recipient the chain's v4 pins name as a sink (a router sentinel, the zero address, a pinned Uniswap v4
  contract) is refused as `recipient_mismatch` for every venue: output paid there would be stranded.
- Behind a backend: use `uniswapRemoteProvider({baseUrl})` in the app — the stub with the shipped pins that also
  declares `ownGasEstimate` (a bare `remoteProvider({...uniswapPins})` broadcasts the backend's quoted gas limit). Turn
  v4 on in the server only after every app it serves ships the pins from 0.5.0 or later: older pins name SwapRouter02
  only, drop the Universal Router or SwapProxy quote, and lose Uniswap on that pair.
- Pool provenance: an app's pins accept only pools from the shipped list (or the `v4ExtraPools` it pins itself with
  `uniswapPinsWith({v4ExtraPools})`). By default (`v4RankedPools: "listed"`) the server never lets a route through an
  unlisted-token grid pool or an extra pool displace the v3 route; `"extra"` ranks extra pools the apps share, `"all"`
  is for a provider running in the app itself.
- A v4 deadline is at most 600 s ahead whatever `deadlineSeconds` says (the bound the pins hold it to, with 60 s of
  clock skew; `uniswapPinsWith({clockSkewSeconds})` allows more).
- The local provider declares `ownGasEstimate`: the engine sends each Uniswap call with the account's own estimate
  (Monad charges the gas limit, not the gas used).

On Monad, 62,000 MON → AUSD pays about 1 AUSD on v3 and about 670 AUSD on v4 (the hookless MON → USDC → AUSD route).

**Uniswap v3 and v4 as two rows.** By default the provider returns one Uniswap quote, the better venue. To show both,
set `venueRoutes: "both"` (with v4 on): `getQuotes` then returns the best v3 route (`routeId: "v3"`) and the best v4
route (`routeId: "v4"`) from one ranking pass — the same reads as one quote, plus the losing venue's own probe and checks
(with `maxPriceImpactBps`, also its spot reads for the gate: 5 calls more on the recorded Monad 62,000 MON pass) — each
built and checked as it would be had it won (impact gate, gas bound, the strict v4 check, the token-input simulation).
One venue refusing never drops the other; a venue left out because its reads failed (rate-limited, unanswered), or
because its deployment does not match its pins (v3's too), is named to the operator through `onV4Warning`. The
router ranks each as its own row; label it from `routeId` and execute the pick with `using("uniswap", routeId)` — a
live request without a `routeId` is the one-quote ranking, which need not match the row shown. A picked route is
quoted on that venue or refused, never swapped for the other, and the pins bind `routeId` to the calldata (a `"v3"`
quote calling the Universal Router is refused).

```ts
uniswapProvider({rpcUrls, v4: "all", venueRoutes: "both"})          // in the app, or on the server
uniswapRemoteProvider({baseUrl: "/api/v2/swap2", multiQuotes: true}) // the app's stub, once the server runs "both"
```

Behind a backend, set `venueRoutes: "both"` on the server first: `/quote` keeps answering with the winner (now naming
its route), so apps without `multiQuotes` keep one Uniswap row; apps then turn on `multiQuotes` for the two rows. A
`multiQuotes` app against a server without `"both"` gets no Uniswap quote at all (no row, and no executable quote).

### Curve

`@anywalletkit/protocol-swap2-curve` swaps on Curve Router NG straight from the contracts: the
router's own `get_dy` prices each candidate route and its explicit-receiver `exchange` executes the
best one, paying only the recipient and reverting under the minimum (never 0). Routes cross one or
two pools, and only pools from a curated allowlist the package pins — generated by
`scripts/build-allowlist.mjs`, checked on-chain (code hash, coins, TVL, age) and reviewed in the
diff. Between two pools a route only passes through a catalog token, the native coin or the pinned
wrapped native; the registered fake-USDT pool and the pools drained in 2023 are refused whatever a
list says. The router's code hash and version are checked before the first quote on a chain, and
right before broadcast the module re-checks the sealed call, each pool's code and coins, and a fresh
`get_dy` against the minimum. On Ethereum the v1.2 router also swaps crvUSD ↔ scrvUSD in one step.

```ts
import { curveProvider } from '@anywalletkit/protocol-swap2-curve'

const curve = curveProvider({ rpcUrls: { 1: ['https://eth.example/rpc'], 42161: ['https://arb.example/rpc'] } })
```

Routers are pinned on 18 EVM chains; a chain is offered only where the allowlist has pools and you
pass an RPC (Ethereum, Arbitrum, Base, OP Mainnet, Gnosis, Monad, Plasma and X Layer today).

- **MEV on Ethereum.** The minimum caps what a sandwich can take at your slippage; it does not stop
  one from taking up to that. Keep the default small slippage on stable pairs and send Ethereum
  swaps through an MEV-protected RPC (a private transaction relay) where you can.
- **No gas limit in the quote.** The router call carries none: the wallet estimates the exact call
  (with headroom) right before broadcast, after any approval. A per-step formula ran some routes out
  of gas and overcharged where the limit is what you pay (Monad).
- **Behind a backend:** `remoteProvider({ name: 'curve', baseUrl, ...curvePins })` checks the call
  on the device; `...curveRemotePins({ rpcUrls })` also checks the build on chain and holds the
  backend's output and minimum to a fresh `get_dy` within the slippage, so the minimum is the
  device's own. If the backend provider sets `defaultSlippageBps`, pass the same value here.

### Relay

`@anywalletkit/protocol-swap2-relay` talks to Relay's own API and verifies the whole order on the
device before anything is signed. A Relay deposit names an order only by its hash; the module asks
for the order behind it, recomputes the hash (EIP-712 `hashStruct`, Relay's types) and requires it
to be the id in the deposit calldata, requires the solver's signature to recover to the pinned
signer, and holds the order to the request: recipient, both chains, both tokens, the exact input
amount, the minimum, the deadlines and every refund recipient. The deposit and the exact ERC-20
approval are then built locally for the depository pinned in the package, never taken from the API.

```ts
import { relayProvider } from '@anywalletkit/protocol-swap2-relay'

const relay = relayProvider() // or { baseUrl: 'https://your-backend.example/relay' }: see the proxy note below
```

- **Named refusals.** A refused quote reads `relay: <what was found> [<code>]` and reaches
  `onRefusal`; through the router it shows in `lastRejections`.
- **What it does not take.** Routes where Relay swaps on the source chain first (the transaction
  would not call the depository), orders with destination calls or their own fees, the
  whole-allowance deposit, and non-EVM chains.
- **Unfilled orders.** Relay refunds on the source chain to the sender; status reports
  `refund-pending` / `refunded`. Status is read from Relay unauthenticated and is for display only.
- **Behind a backend:** `remoteProvider({ name: 'relay', baseUrl, ...relayPins })` runs the same
  checks on the device against the quote and the built transaction.
- **What a proxy or backend can still do.** It cannot change the recipient, chains, tokens, refund
  addresses or the minimum shown. It can make the quote worse: the solver signs whatever request
  reaches Relay, so one forwarded with an app fee or a gas top-up returns a genuine order with a
  lower amount. The module refuses a quote that accounts for either and always names the slippage
  (yours, else 2 %), but the price itself is bounded only by your `minAmountOut` or the router's
  other quotes.
- **One deposit per order.** Cleared order ids are remembered for the JS realm; pass `clearedStore`
  to keep them across app restarts.

### 0x

`@anywalletkit/protocol-swap2-0x` quotes 0x's Swap API v2 through the Permit2 flow: same chain,
exact input. The API needs a key on every request, so the provider with the key runs on your
server only (under React Native it refuses a key outright) and the app uses the remote provider,
which checks everything that comes back on the device before the engine signs.

```ts
// your server: the key stays here (a getter, or a string from your env)
import { zeroExProvider } from '@anywalletkit/protocol-swap2-0x'
const zeroex = zeroExProvider({ apiKey: () => process.env.ZEROEX_API_KEY, rpcUrls: { 8453: ['https://base.example/rpc'] } })
// … pass it to createSwap2Handler({ providers: [zeroex, …] })

// the app: no key, its own RPC for the Settler registry
import { zeroExRemoteProvider } from '@anywalletkit/protocol-swap2-0x'
const zeroexInApp = zeroExRemoteProvider({ baseUrl: 'https://your-backend.example/api/swap2', rpcUrls: { 8453: ['https://base.example/rpc'] } })
```

- **The Settler comes from the chain.** The call target must be the Settler 0x's registry names
  now (or the one before it), read over the app's own RPC. It must be an address the registry
  deploys Settlers to (CREATE3, computed on the device), between the deployments the chain table
  pins as previous and current (`previousLiveNonce`, `newestLiveNonce`) plus two newer ones for
  token sales, and a contract (`eth_getCode`): an RPC can name only a deployed 0x Settler. A
  native-coin sale goes only to the two pinned Settlers, since its value is sent to the address
  as it is. A newer deployment is refused, with what to do, until the pins are raised; the watch
  job reports each one the day it happens. Right before the broadcast the registry is read again
  on the device (in remote mode before the backend's preflight), and a native sale's quote stays
  valid for at most two minutes.
- **What the account signs.** A token sale is paid with a Permit2 signature transfer: exactly the
  input, of the token sold, usable only by that Settler, valid for at most ten minutes. The engine
  rebuilds the EIP-712 payload itself, asks the account to sign it (the account needs
  `signTypedData`) before the exact approval to Permit2 goes out, and appends the signature to
  the calldata. `plan.source.permit2Transfer` on the review screen is that payload. A native-coin
  sale signs nothing and approves nothing.
- **What the call does.** Recipient, buy token and minimum are read from the Settler's own slippage
  check; the first action must spend exactly that permit (a native sale's must be `NATIVE_CHECK`).
  The guarantee is the minimum: 0x keeps any surplus above the quoted amount (visible in the
  calldata), and a buy token with a transfer tax 0x does not flag can arrive short of it.
- **Gas.** Every call — the signed one and a native sale — is dry-run from the account and goes out
  with the account's own estimate, not the quoted limit.
- **Signing policies.** A kit allowlist must list Permit2, the token and the Settler, which rotates.
  `zeroExKnownSpenders(provider, chainId)` gives the Settlers the provider's own resolver read, as
  `{ [settler]: "0x Settler" }`: pass it as `knownSpenders` to `describeTypedData`
  (`describeTypedData(typed, { chainId, account, knownSpenders: await zeroExKnownSpenders(zeroexInApp, 8453) })`)
  and spread its keys into the allowlist, rather than a fixed address.
- **Flags.** The SDK reads no environment; by convention the app and the backend use
  `ZEROEX_ENABLED` (dark unless set) and `ZEROEX_API_KEY`.

### Across

`@anywalletkit/protocol-swap2-across` bridges the same asset between 17 EVM chains (USDC, USDT /
USDT0, ETH / WETH, WBTC; Ethereum, Optimism, Base, Arbitrum, Polygon, Unichain, Linea, zkSync Era,
World Chain, Ink, Avalanche, Monad, HyperEVM, MegaETH, Robinhood Chain, Arc, Plasma) with one
transaction: a **direct deposit** — `deposit(...)` on the source chain's SpokePool. A relayer pays
the recipient on the destination from its own funds, usually within seconds, and is repaid from
the deposit.

```ts
// On your server (the Across API V5 key never ships in an app):
import { acrossProvider } from '@anywalletkit/protocol-swap2-across'
const across = acrossProvider({ apiKey: () => process.env.ACROSS_API_KEY, rpcUrls }) // behind createSwap2Handler

// In the app:
import { acrossRemoteProvider } from '@anywalletkit/protocol-swap2-across'
const across = acrossRemoteProvider({ baseUrl: 'https://your-backend.example/swap2', rpcUrls })
```

- **What is verified.** The deposit is encoded on the device from the SpokePool pinned in the
  package and the user's own request, and checked again right before signing: the depositor is the
  signing account (an Across depositor can redirect the output, so a refund address the caller names
  is refused), the recipient, both tokens, the exact input, the destination chain, an empty message
  (nothing runs on arrival), a fill deadline two hours after the quote time, no exclusive relayer,
  the fee within your cap (`maxFeeBps`, default 10 %) and at least what relayers take on that asset
  (stablecoins 1 bp, ETH from Ethereum 0.7 bp, ETH from Optimism, Base or Arbitrum 4.5 bps, ETH from
  another L2 0.7 bp, WBTC 2.5 bps), and the fees the quote shows (which your engine's
  `maxProtocolFeeBps` adds up) equal to the deposit's. An ERC-20 is approved for exactly the input,
  to the SpokePool. A backend can choose only the output amount inside those bounds.
- **The app reads Across's relayer fee itself.** For every quote the backend sends,
  `acrossRemoteProvider` asks Across's keyless `/suggested-fees` (from the app: allow
  `https://app.across.to` in a browser's CSP `connect-src`) and refuses a deposit that leaves
  relayers more than 10 % under it, so a backend cannot get a deposit signed that nobody would fill,
  or win the comparison of routes with one. Without an answer only Ethereum, Optimism, Base and
  Arbitrum to Optimism, Base and Arbitrum stand, on the per-asset floor; `suggestedFeesUrl: null`
  turns the read off with the same fallback. Right before signing the deposit is checked again by
  the device's clock.
- **Where the price comes from.** Across API V5 quotes its own route (an execution step on the
  origin chain, sometimes another rail), which a direct deposit does not take: its `nextActions`
  are never run. The module asks V5 for the price and Across's relayer fee quote
  (`/suggested-fees`, keyless) for what a relayer needs, and leaves relayers the larger of V5's fee
  net of its origin step and that relayer fee — the relayer fee alone when V5 prices another rail
  (a fill estimate over a minute: its price is that rail's, not a direct deposit's). If
  `/suggested-fees` stops answering, a floor pinned
  from the fills of plain deposits stands in on Ethereum, Optimism, Base and Arbitrum (the server
  then needs `rpcUrls` for Ethereum and the source chain, for the quote time); other routes are
  refused rather than priced on a guess. Ethereum as a destination is not priced yet.
- **Refunds and timing.** A deposit nobody fills can no longer be filled after its fill deadline
  (two hours after the quote time); Across then refunds the input to the depositor on the source
  chain through its settlement bundles, which takes hours more. Status reads the chains themselves
  (the deposit's event on the source chain, `fillStatuses` on the destination): `pending`, then
  `completed`, or `expired` once the deadline has passed unfilled. With `rpcUrls` for both chains
  the app reads it without the backend.
- **Named refusals.** `across: <what was found> [<code>]`, each with a reason (`route-unpriced`,
  `relayer-price`, `api-error`, `tx-fee`, …).

### Stargate

`@anywalletkit/protocol-swap2-stargate` moves USDC, USDT and ETH (and the OFT assets pinned in the
package) between 15 EVM chains with Stargate V2 **Taxi**: one `sendToken` call on the source chain,
priced straight from the pinned pools, no API key. It is off until `enabled: true`. New transfers use
Taxi only (Stargate retired Bus on October 1, 2026), and transfers involving Scroll are refused from
2026-12-08, Stargate's sunset date for that chain.

```ts
// On your server, behind createSwap2Handler (RPCs for the source AND the destination chain):
import { stargateProvider } from '@anywalletkit/protocol-swap2-stargate/provider'
const stargate = stargateProvider({ enabled: true, rpcUrls: { 'eip155:42161': ARBITRUM_RPC, 'eip155:8453': BASE_RPC } })

// In the app: the pins check every build and prove delivery with the app's own RPCs.
import { remoteProvider } from '@anywalletkit/protocol-swap2-core/remote'
import { stargatePins } from '@anywalletkit/protocol-swap2-stargate/pins'
const providers = [remoteProvider({ name: 'stargate', baseUrl, headers, ...stargatePins({ rpcUrls }) })]
// new RouterSwap2Protocol(account, { fromChain, providers, reviewExecution, operationStore })
```

- **What is verified.** The device rebuilds the whole `sendToken` calldata from the quote's intent
  (pool, destination, recipient, amount, minimum, messaging-fee cap) and refuses any byte of
  difference. ERC-20s are approved for exactly the input; native pools are never approved.
- **Delivery is proven, not reported.** A transfer is `completed` only when the destination pool's
  payout is read from finalized receipts on both chains with the app's RPCs; the backend's status
  cannot stand in for it. Quotes carry no ETA (`etaSeconds: null`), so Stargate is never tagged
  `fastest`.
- **Keep a journal.** Pass an `operationStore` and pass the reviewed `toTokenAmountMin` as
  `minAmountOut`. On `Swap2MaybeSentError`, resume the operation id; never send again. Cached tokens
  and undelivered LayerZero messages are recovered by a separate, reviewed and paid action
  (`recoverSwap2`).
- **Compose (opt-in).** With `compose: { enabled: true }` on both the provider and the pins, a USDC or
  USDT source can deliver another ERC-20 on Ethereum (`routeId: 'compose'`): Taxi into the pinned
  LI.FI receiver plus one Uniswap V3 swap the SDK encodes itself. If the swap does not run, the
  bridged stablecoin is paid to the recipient on Ethereum and the route reports `partial`.

### KyberSwap

`@anywalletkit/protocol-swap2-kyberswap` routes a same-chain swap through KyberSwap's aggregator on 18
EVM chains and settles it through MetaAggregationRouterV2. No integrator fee is charged.

```ts
import { kyberswapProvider } from '@anywalletkit/protocol-swap2-kyberswap'

// On your server (the key never ships in an app):
const kyber = kyberswapProvider({ apiKey: process.env.KYBERSWAP_API_KEY, rpcUrls: { 8453: ['https://base.example/rpc'] } })
// In the app, behind that server:
// remoteProvider({ name: 'kyberswap', baseUrl, ...kyberPins })
```

- **Keyless or keyed.** Without `apiKey` the public API is used (a few requests per second per IP).
  With a key, requests go to `https://api.kyberswap.com/swap` with only `X-Api-Key`.
- **Nothing in the build is trusted.** The calldata is decoded strictly and refused unless it is
  `swap()` on the pinned router with the pinned executor, the request's tokens, amount and receiver, a
  minimum at least the quote's and your floor, and no fees, permit or extra flags. `kyberPins` makes
  the app run the same check on a backend's quote.
- **Simulated first.** A native input is simulated with a balance override. A token input's approval
  and swap run as one simulated block before any approval is sent, so a route that reverts never
  costs the user an approval. Execution needs `rpcUrls` for the chain.
- **Price impact.** `providerData.priceImpactBps` comes from KyberSwap's own USD valuation, so the
  router can warn about a bad route even when your app has no price for the tokens.
- `destAmount` is KyberSwap's quote, a ceiling: executed outputs come a few basis points under it, and
  KyberSwap keeps any output above the quote.

### CoW Protocol

`@anywalletkit/protocol-swap2-cow` places the swap as an order: the account signs it, CoW's solvers
compete to fill it, and the network cost is taken from the sold token. It ships off — pass
`enabled: true` (and `enabledChains` to roll out chain by chain).

```ts
import { cowProvider } from '@anywalletkit/protocol-swap2-cow'

const cow = cowProvider({ enabled: true, enabledChains: [8453], rpcUrls: { 8453: ['https://base.example/rpc'] } })
```

- **Selling a token** costs no gas when the token has EIP-2612 `permit` (the account signs the
  permit, then the order) or is already approved; otherwise one exact approval to the vault relayer
  comes first. The permit needs `rpcUrls`.
- **Selling the native coin** is one transaction to eth-flow (`createOrder`); the coin is held by the
  contract until the order fills, and returns if it expires. `claimSwap2(id, account)` builds that
  refund when CoW's refund service has not sent it.
- **Signing is EIP-712 typed data only**, so the account must implement `signTypedData`; the module
  never asks for a signature over a bare order digest.
- **An order is not a transaction.** `swap2()` returns once the order is placed; the status stays
  `pending` until a solver fills it or it expires (20 minutes by default). An unfilled token order
  costs nothing — the tokens never left the account.
- **Cancel** with `cancelSwap2(id, account)` (a signed request to the orderbook, free) or
  `cancelSwap2(id, account, { onchain: true })` (a transaction, binding).
- **Checked before signing:** the order is written on the device from the request; the quote only
  fills in amounts, which are held to the slippage and the caller's minimum. The settlement
  contract, vault relayer and eth-flow are pinned per chain; the signed fee is always 0; appData is
  the hash of the document the module wrote (no partner fee, no hooks but its own permit).
- **Runs on the device** against the public orderbook (`api.cow.fi`), no key. It is not meant to sit
  behind `remoteProvider`.

## 3. Describe the swap

<Snippet file="swap/src/swap.ts" region="options" />

- `fromToken`: a token on the **source** chain, as its contract address or a catalog symbol

- `toToken`: the token on the **destination** chain, as that chain's own id: a contract

## 5. Let the user pick a route

<Snippet file="swap/src/swap.ts" region="routes" />

Routes come back ranked by value. Two of them are tagged:

- **`best`**: the highest value. Routes within 0.2% of each other count as the same price;
  inside that band the faster and more reliable route wins.
- **`fastest`**: the lowest estimated time. A route without an estimate (Stargate's, for one) is never
  `fastest`; when no route has one, `routes.fastest` is `null`.

For a real USDC Ethereum → Base quote on 100 USDC, this returned four routes: CCTP
tagged `best` (99.989 USDC guaranteed, ~3 minutes), LI.FI tagged `fastest` (99.735 USDC,
seconds), then NEAR Intents and THORChain. For 25 USDT from Ethereum to USDT0 on Arbitrum,
USDT0 came out `best` (exactly 25 guaranteed, ~17 minutes) and LI.FI `fastest`.

Pass `valueUsd: usdValue(prices)` to the router to rank on net USD value: native bridge fees
are then subtracted. Add `sourceGasUsd: evmSourceGas({prices, rpcUrl})` to subtract the source
gas too (EVM sources): the venue's gas limit for a calldata route, a transfer for a deposit
route, nothing for a gasless one (a CoW order, an Omniston EVM → TON order), plus an ERC-20
approval unless the sender's allowance already covers it, at the chain's gas price. On Ethereum
at small amounts this moves the pick (a $50 USDC bridge: a plain deposit over approve + burn); on
L2s gas is cents and rarely changes it. `evmSourceGas({prices, rpcUrl, useGasEstimate: true})`
prices a quote's `gasEstimate` (the gas its transaction is expected to use) instead of the limit
when the quote states one, so a venue is not charged for the headroom in its limit; venue figures
are passed on as stated (protocol-swap2-core's README lists how far each runs from the gas used).

### Compare the on-chain venues at one block

Uniswap, Curve and Balancer price from the chain's state. Asked separately at "latest", the
quotes of one round can come from different blocks. Read `eth_blockNumber` once per source
chain and pass it to the round: `quoteSwap2Routes(options, {blockNumber})`, or `blockNumber` in
the `QuoteParams` of `router.getQuotes`. Those venues then price at that block and say so on each
route (`route.blockNumber`); API venues ignore it. A node that does not have the block is asked
on the next endpoint, then the venue refuses with `stale_node`, never quoting "latest" in its
place. Use `latest` (or `latest − 1` on fast chains), only for the comparison round: the execution
re-quote reads "latest", and every check and simulation always does. Ethereum, Base and Monad,
2026-11-28: every Uniswap v3 and v4, Curve and Balancer quote of a round named the same block.

## 6. Execute

<Snippet file="swap/src/swap.ts" region="execute" />

Before anything is signed, the router fetches a live quote from the chosen provider and
checks it against what you showed:

- the output is not below your `minAmountOut`;
- the recipient, amounts and chains match the request;
- the transaction sends exactly the quoted amount, and any transfer or approval inside it
  names only your account, the quoted deposit address or the declared spender;
- aggregator calls go only to that provider's audited contracts.

A route that fails any check is refused, and nothing is sent. ERC-20 approvals are for the
exact amount, never unlimited, and are revoked again if the swap fails after approving. On
Ethereum, USDT is reset to zero first, as that token requires.

A relayer pays exactly the deposit's `outputAmount`, so an Across quote's minimum equals its output. The engine quotes again at execution: pass `minAmountOut` a few bps under the quote (`suggestSlippage` gives at least 5), or a re-quote a few base units lower refuses the swap.

### Show a review screen

<Snippet file="swap/src/swap.ts" region="review" />

`plan` holds exactly what will be signed: provider, amounts, guaranteed output, approvals,
ETA and the source transaction itself. For a Permit2 swap (0x) the source call also carries
`permit2Transfer`, the EIP-712 payload the account signs before the call; show it too.

## 7. Track delivery

A cross-chain swap finishes on another chain, minutes later. Poll its status with the id
returned by `swap2()`:

<Snippet file="swap/src/swap.ts" region="status" />

| Status | Meaning |
|---|---|
| `pending` | In flight |
| `action-required` | Two-phase route (CCTP): the user must claim on the destination chain |
| `completed` | Delivered |
| `refund-pending` / `refunded` | The provider is returning / has returned the funds |
| `failed`, `expired`, `cancelled`, `partial` | Final, not delivered in full |

The id is a string (`awk1.<provider>.…`). Store it with the user's activity: it is all you
need to resume tracking after an app restart.

### Refusal reasons

A refusal keeps its text, which is meant for logs and support. To decide what to show the user, switch on its
`reason` instead of matching the text. `refusalOf(err)` reads the reason from the error, or from the first error in
its `cause` chain that has one:

```ts
import { refusalOf } from '@anywalletkit/protocol-swap2-core'

try {
  await swaps.quoteSwap2(options)
} catch (err) {
  const refusal = refusalOf(err)
  switch (refusal?.reason) {
    case 'amount_too_small': return show('Increase the amount')
    case 'unsupported_pair': return show('This pair is not supported')
    case 'rate_limited': return retryIn(refusal.retryAfterMs ?? 5_000)
    default: return show('No route right now')
  }
}
```

| `reason` | Meaning |
|---|---|
| `no_route` | The venue has no route for this request, or the venues that sat out did so for different reasons |
| `unsupported_pair` | The venue does not serve this chain, token, pair, direction or flow |
| `amount_too_small` / `amount_too_large` | Outside the venue's limits (fees above the output count as too small) |
| `insufficient_liquidity` | The venue reports too little liquidity for the amount |
| `rate_limited` | The venue throttled the request. `retryAfterMs` is set when it said how long to wait |
| `key_rejected` | The venue rejected the API key, or its absence |
| `upstream_unavailable` | The venue failed, timed out or answered in another shape. `httpStatus` is set when there was one |
| `chain_halted` | The chain, its trading, or the venue's handling of it is halted or paused |
| `recipient_unverifiable` | The transaction does not bind the delivery to a recipient the SDK can check |
| `recipient_mismatch` | The transaction pays or refunds an address other than the requested one, or one that cannot receive |
| `vault_mismatch` | The deposit target (vault, inbound address, router, escrow, settlement contract) is not the confirmed or pinned one |
| `stale_node` | The node or indexer that answered trails the chain too far to be trusted |
| `quote_expired` | The quote or its deadline ran out |
| `price_check_failed` | The output, floor, slippage or value fails the check |
| `simulation_failed` | The transaction reverted in simulation or preflight |
| `policy_refused` | A policy of your app or of the SDK refuses it: fee caps, sponsorship, a disabled provider, addresses the app did not allow |

Where the reason travels:

- **The engine's "no route available"** (`Swap2QuoteError`) has `refusals`: each venue's refusal as
  `{ provider, message, reason?, retryAfterMs?, httpStatus? }`. Its own `reason` is the venues' shared reason, or
  `no_route` when they differ. With no venue to ask, the list says why while the message stays as it was: the
  disabled venues that serve the pair (`policy_refused`), or `unsupported_pair`.
- **The router** keeps the same list in `lastRefusals`, next to `lastRejections`, and in `RouteSet.refusals`;
  `refusalsFor(params)` gives one auction's list when quotes overlap.
- **`onRefusal`** gets the classification as a second argument: `onRefusal(text, { reason, retryAfterMs?, httpStatus? })`.
- **A swap2 server** adds `reason` (and `retryAfterMs`, `httpStatus`) to its error bodies and to `noQuote`. The
  `remoteProvider` stub puts it back on the error. A status alone also classifies: 429 → `rate_limited` (with
  Retry-After), 401 / 403 → `key_rejected`, 408 / 425 / 5xx → `upstream_unavailable`.
- **Provider pins** (`lifiPins`, `thorchainPins`, …) classify their own refusal texts through `reasonOf`, so a remote
  stub's "fails this app's own check" carries a reason too.

A refusal without `reason` is not classified. `refusalOf` reads only reasons the SDK set: a wallet's
`SimulationError` keeps its own `reason` field (the revert text, which a contract chooses), so check
`err.name === 'SimulationError'` for those. A `Swap2MaybeSentError` never has a reason: do not retry it.

## Fee caps

`maxNetworkFeeBps` and `maxProtocolFeeBps` (basis points of the input) refuse routes whose
**itemized** fees are above the cap. The check is fail-closed: a route whose provider does
not itemize its fees is refused whenever a cap is set, and so is one whose capped fees are not in the
input token. For a native-coin input, the native coin counts under the names providers give it:
`native`, and on EVM chains the zero address or `0xEeee…EEeE`. With caps on, the USDC example above
keeps only the CCTP route. To protect the user without losing routes, compare the
guaranteed output (`toTokenAmountMin`) instead.

### Native fee ceiling

Some bridges charge native coin on top of the input (a LayerZero messaging fee, for example),
declared in the quote. `swap2()` refuses such a fee above the chain's cap: 0.005 ETH on
Ethereum and on chains without a cap of their own (Arbitrum, Base, …), 100 CELO on Celo,
20 POL on Polygon, and so on. The error reads
`swap2: quoted native fee <fee> exceeds the cap <cap> for <chain>`.

To allow one route above it, set `nativeFeeCeiling` on the router (or on any swap2
protocol). The engine calls it for every execution pass whose quote declares a native fee, before
that pass's review screen and approvals: once, unless the quote expires during an approval and the engine
re-quotes (the fresh quote is asked again, and a refusal then revokes the allowance just granted):

| The hook returns | Result |
|---|---|
| a non-negative `bigint` | the cap for this execution, higher or lower than the chain's (`0n` refuses any fee) |
| `undefined` | the chain's cap, as without the hook |
| anything else, or throws | the swap is refused (`Swap2ConfigurationError`) |
| more than `ctx.maxCeiling` (20 × the chain's cap: 0.1 ETH on Ethereum, 2000 CELO on Celo) | the swap is refused |

No answer removes the cap. Return `undefined` for every route you do not mean.

USDT0 Legacy Mesh into Tron is the case this was built for. Its LayerZero fee was
0.005341 ETH from Ethereum and Arbitrum and 170.5 CELO from Celo on 2026-11-12. With the
provider's 25 % headroom the quote declares 0.006676 ETH and 213.1 CELO, both above the
default caps. Tron is LayerZero endpoint 30420, and the `usdt0` provider's mesh intent ids
read `usdt0-mesh:<source eid>:<destination eid>`:

```ts
const TRON_MESH_CEILING = new Map([
  ['eip155:1', 10n ** 16n],             // 0.01 ETH on Ethereum
  ['eip155:42161', 10n ** 16n],         // 0.01 ETH on Arbitrum
  ['eip155:42220', 300n * 10n ** 18n],  // 300 CELO on Celo
])

const swaps = new RouterSwap2Protocol(account, {
  fromChain: account.chain,
  providers,
  nativeFeeCeiling: ({ provider, intentId, fromChain, destChain }) =>
    provider === 'usdt0' && destChain === 'tron:728126428' && /^usdt0-mesh:\d+:30420(?:~|$)/.test(intentId)
      ? TRON_MESH_CEILING.get(fromChain)
      : undefined,
})
```

`destChain` is always the catalog id (`tron:728126428`), even when you passed
`tron:0x2b6653dc`. Through a swap2 server the intent id ends in `~<token>`, which the
pattern above allows. The cap applies only when the swap executes: `quoteSwap2Routes` still
lists a route whose fee is above it.
