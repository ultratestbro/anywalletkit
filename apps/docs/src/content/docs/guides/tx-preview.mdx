A review screen that shows only "to: 0x1231…" and "data: 0x095ea7b3…" asks the user to trust
blindly. `tx-preview-evm` turns one call, or an approve → call sequence, into what the user
needs to see before signing:

- **Decoded calls.** Approvals (ERC-20 `approve`, `increaseAllowance` and `increaseApproval`, an
  EIP-2612 `permit` call, Permit2 `approve` and `permit`, single or batch, `setApprovalForAll`),
  token transfers, and the name of every contract you list as known. A Permit2 batch puts every
  allowance in `approvals` (the first one is also `approval`).
- **Simulated balance changes.** The whole sequence runs in one simulated block through
  `eth_simulateV1` with transfer tracing: "-100 USDC, +0.03 ETH".
- **Checks.** Named outcomes (`approval-unlimited`, `simulation-reverted`,
  `recipient-foreign`…) that your app turns into its own words.

Nothing is signed or sent. The module only reads, through your RPC. Snippets come from
[`examples/tx-preview`](https://github.com/ultratestbro/anywalletkit/tree/main/examples/tx-preview), which our CI typechecks and tests.

```sh
npm install @anywalletkit/tx-preview-evm
```

## RPC

The module takes a function `(method, params) → result`, so any transport works:

<Snippet file="tx-preview/src/preview.ts" region="rpc" />

Pass JSON-RPC errors through with their `code` and `data`: the module uses them to tell a
revert from a node that has no `eth_simulateV1`.

Balance changes need `eth_simulateV1`. On public endpoints we checked (October 2026) it is
served on Ethereum, Base, Arbitrum, Optimism, Polygon and BNB Chain, and missing on
Avalanche. Where it is missing, a single call falls back to `eth_call`, which tells pass from
revert but shows no balance changes. A sequence can't be simulated there at all
(`simulation.status: 'unavailable'`).

## Preview a transaction

<Snippet file="tx-preview/src/preview.ts" region="preview" />

| Input | Meaning |
|---|---|
| `calls` | Run in order in one block: approvals first, then the call |
| `own` | Every address of this user; a transfer to one of them is not "foreign" |
| `known` | Contracts you trust → the name to show (a provider's routers, your tokens) |
| `expectedRecipient` | Where a same-chain swap's output should arrive. It is a recipient check, and with a simulation the output going anywhere else is flagged (`output-missing`, `output-foreign`). Leave it out for a bridge (and for anything else whose output does not arrive on this chain in this transaction) |
| `expectedOutputToken` | The token the same-chain swap buys (`plan.destToken`; the zero address, `0xEeee…` or `"native"` for the gas coin). The output checks then read exactly that token. Without it they read every token the sender doesn't spend, which is weaker: pass it whenever you pass `expectedRecipient` |
| `expectedApproval` | The allowance the flow needs; a larger approval is flagged |
| `stateOverrides` | Simulate with a different balance, nonce or code, e.g. to preview a flow before the account is funded |
| `native` | Symbol and decimals of the gas coin (default ETH, 18) |

The result has three parts:

- **`calls`.** Each call with `method`, `label`, and `approval` or `transfer` when decoded.
  An approval's `amount` is `null` when it is unlimited (2²⁵⁵ or more) or an operator
  approval.
- **`simulation`.** One of three statuses:
  - `ok`: `changes` (signed deltas in base units, with symbol and decimals), `gasUsed`, and `transfers`
    (every token and native movement of the sequence, whoever sends or receives it);
  - `reverted`: `callIndex` and `reason`;
  - `unavailable`: `reason`.
- **`checks`.** `{ code, status: 'ok' | 'warn' | 'unknown', detail }`.

Balance changes count ERC-20 `Transfer` events to and from the sender, plus native transfers.
WETH-style `Deposit` / `Withdrawal` events count only for contracts in `known`, so a
look-alike event from an arbitrary contract can't fake a balance change.

## Turn checks into a verdict

Checks are codes, not text. The wording, the language and how strict to be are your app's
decisions:

<Snippet file="tx-preview/src/preview.ts" region="verdict" />

| Code | Status | Meaning |
|---|---|---|
| `contract-known` / `contract-unknown` | ok / warn | A contract a call goes to is in `known`, or isn't — one per target, every call but approvals (a transfer-shaped call included) |
| `simulation-ok` | ok | Simulated; balance changes are in `simulation.changes` |
| `simulation-reverted` | warn | It will fail; `detail.reason` says why |
| `simulation-unavailable` | unknown | The network can't simulate it |
| `recipient-own` / `recipient-foreign` | ok / warn | A recipient is, or isn't, one of `own` |
| `output-missing` | warn | With `expectedRecipient`: the sequence spends, and nothing (of `expectedOutputToken`, when given) arrives at the recipient (`detail.address`) |
| `output-foreign` | warn | With `expectedRecipient`: more than 5 % of the swap's total output ends at addresses that are not the recipient and not one of `own`, all of them together. `detail.token`, `detail.amount` (their total), `detail.address` (the largest holder) and `detail.holders` (when more than one). A pool or router that passes the output on holds none of it, so it isn't counted; fees and token taxes up to 5 % of the output are |
| `approval-exact` | ok | Approves no more than `expectedApproval` |
| `approval-unchecked` | unknown | A bounded approval and no `expectedApproval` to compare it with |
| `approval-excess` | warn | Approves more than `expectedApproval` |
| `approval-unlimited` | warn | Unlimited allowance (≥ 2^128 − 1) or operator approval |
| `approval-unknown-spender` | warn | The spender is not in `known` |
| `approval-unparsed` | warn | A `permit` selector (EIP-2612 or Permit2) whose arguments can't be read: it may grant an allowance nobody can size |
| `native-value` | ok / warn | A call sends native coin into a contract (`detail.amount`, per call); warn when that contract is not in `known` (`detail.address`) |

## Preview every write

Policies call `confirm` before every write, which makes it the place to simulate. The
`intent` carries the call as `raw`:

<Snippet file="tx-preview/src/preview.ts" region="confirm" />

`ask` receives the preview, or `null` for writes with nothing to simulate (message
signatures, typed data, non-EVM chains), and shows your sheet. With this in the wallet's
policies, no EVM transaction reaches the key without a simulation the user has seen. See
[Policies](/concepts/policies/).

## Preview a swap

The swap router hands the exact plan to `reviewExecution` before the first approval. Preview
the approvals and the source call together, the way they will run:

<Snippet file="tx-preview/src/preview.ts" region="swap" />

`expectedApproval: plan.sourceAmount` flags a route that asks for more than it spends. For a
same-chain swap, `expectedRecipient` with `expectedOutputToken: plan.destToken` flags output that doesn't arrive at the
recipient or ends at a third party (a bridge's output arrives on another chain, so the example passes them only when both
chains are the same). Wire it into
the router as shown in [Swaps → Show a review screen](/guides/swaps/#show-a-review-screen).
